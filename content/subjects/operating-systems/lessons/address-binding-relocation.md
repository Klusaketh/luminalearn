## Introduction

A compiled program is full of memory addresses: the location of each variable, the target of each jump, the entry point of each function. But when the program is written, nobody knows where in physical memory it will eventually run, because that depends on which other programs happen to be loaded at the time. And two copies of the same program, running at once, cannot both use the same physical addresses.

Somewhere between writing the program and running it, each symbolic name such as `count` or `print_report` must be turned into a concrete physical location. This is **address binding**, and when it happens determines how flexibly the operating system can place, move, and protect programs. This lesson follows a program from source code to memory, introduces the distinction between **logical** and **physical** addresses that underpins all modern memory management, and shows the simplest hardware that implements it, the base and limit registers.

**Before you start:** you should know what a process's address space contains and the difference between user and kernel mode.

## Core theory

### From source code to a running process

1. The **compiler** translates source code into an **object file**. Addresses inside it are relative to the start of the file, and references to other files' functions are left as unresolved symbols.
2. The **linker** combines object files and libraries into one **executable**, resolving symbols and assigning each part an address in the program's layout.
3. The **loader** (part of the OS) places the executable in memory, sets up its stack and heap, and starts it.

Addresses can be bound to physical locations at any of three stages:

| Binding time | How | Consequence |
| :--- | :--- | :--- |
| Compile time | the compiler produces **absolute code** for a known location | the program must always load at that address; moving it requires recompiling |
| Load time | the compiler produces **relocatable code**; the loader adds the load address to every address field | the program can load anywhere, but cannot move once running |
| Execution time | addresses stay relative while running; hardware translates every access | the program can be moved during execution; needs a memory-management unit |

Compile-time binding was used in simple early systems; MS-DOS `.COM` programs, for example, always loaded at the same offset. Modern general-purpose systems use **execution-time binding**.

### Logical and physical addresses

- A **logical address** (also called a **virtual address**) is one generated by the CPU while running the program. The set of logical addresses a program can generate is its **logical address space**.
- A **physical address** is the one actually sent to the memory hardware.

With compile-time and load-time binding, the two are the same. With execution-time binding, they differ, and a hardware device, the **memory-management unit (MMU)**, translates every logical address into a physical one at run time. The program, and the programmer, only ever see logical addresses.

### Relocation and limit registers

The simplest MMU uses two registers per process:

- the **relocation (base) register** holds the smallest physical address of the process's memory region;
- the **limit register** holds the size of the region.

For every memory access with logical address $a$:

$$\text{if } 0 \le a < \text{limit}: \quad \text{physical} = \text{base} + a; \qquad \text{otherwise: trap (addressing error).}$$

This one mechanism provides both **relocation**, since the process can be placed anywhere and moved by changing the base register, and **protection**, since it cannot reach memory outside its region. Loading the base and limit registers are **privileged instructions**, done by the dispatcher on each context switch.

### Dynamic loading

With **dynamic loading**, a routine is not loaded until it is first called. The program starts with only its main part in memory; calling an unloaded routine triggers the loader. Rarely used code, such as error handlers, never consumes memory if it is never needed. It is a technique programs use themselves (for example, with plug-ins loaded on demand) and needs no special OS support beyond library functions.

### Dynamic linking and shared libraries

**Static linking** copies library code into every executable. **Dynamic linking** postpones linking until run time: the executable contains a small reference, and the code of a **shared library** (`.so` files on Linux, `.dll` on Windows, `.dylib` on macOS) is mapped in when the program starts or when the routine is first used.

- **One copy in memory:** many processes share the same physical pages of the C library, saving memory.
- **Updates without relinking:** fixing a bug in a shared library fixes every program that uses it, after a restart.
- **Version risk:** a program may break if a library changes incompatibly, a problem nicknamed "DLL hell"; systems use version numbers in library names to manage it.

Shared libraries are compiled as **position-independent code**, which works at whatever address it is mapped, and the OS's help is needed so that one physical copy can appear in several processes' address spaces.

### Swapping

A process can be **swapped** out of memory to a **backing store** (disk) and later brought back, possibly to a different place if binding is at execution time. Swapping whole processes is slow, because the transfer time is proportional to the amount of memory moved. Modern systems instead swap individual **pages**, as later lessons describe; mobile systems often avoid swapping and terminate background apps instead.

## Worked examples

### Example 1: A base-and-limit MMU

A process is loaded at physical address 300040 with a region of 120900 bytes.

```python
class MMU:
    def __init__(self, base, limit):
        self.base, self.limit = base, limit          # loaded by the OS on a context switch

    def translate(self, logical):
        if not 0 <= logical < self.limit:
            raise MemoryError(f"trap: logical address {logical} outside limit {self.limit}")
        return self.base + logical

mmu = MMU(base=300040, limit=120900)
for logical in (0, 346, 120899, 120900):
    try:
        print(f"logical {logical:>6} -> physical {mmu.translate(logical)}")
    except MemoryError as error:
        print(error)

mmu.base = 500000                                    # the OS moves the process
print("after relocation:", mmu.translate(346))
```

Output:

```text
logical      0 -> physical 300040
logical    346 -> physical 300386
logical 120899 -> physical 420939
trap: logical address 120900 outside limit 120900
after relocation: 500346
```

The highest legal logical address is 120899, which maps to physical address 420939, the last byte of the region. Address 120900 is one past the end and causes a trap to the kernel. After the OS copies the process to a new region and updates the base register, the same logical address 346 refers to a different physical address. The program never notices it has moved.

### Example 2: Load-time relocation

Before MMUs, a loader bound addresses by patching them. A relocatable executable lists the positions of all address fields (its **relocation table**), and the loader adds the load address to each.

```python
program = [                          # (instruction, operand); operands at listed offsets are addresses
    ("LOAD", 40),                    # load the variable stored at offset 40
    ("ADD", 1),                      # add the constant 1 (not an address)
    ("STORE", 40),
    ("JUMP", 0),                     # jump back to the start of the program
]
relocation_table = [0, 2, 3]         # indices of instructions whose operand is an address

def load(program, relocation_table, load_address):
    image = list(program)
    for i in relocation_table:
        op, operand = image[i]
        image[i] = (op, operand + load_address)
    return image

print(load(program, relocation_table, 1000))
print(load(program, relocation_table, 5000))
```

Output:

```text
[('LOAD', 1040), ('ADD', 1), ('STORE', 1040), ('JUMP', 1000)]
[('LOAD', 5040), ('ADD', 1), ('STORE', 5040), ('JUMP', 5000)]
```

The constant 1 is left alone because it is not an address; that is why the relocation table must say which fields to patch. The program can be loaded anywhere, but once patched, its addresses are fixed: moving it would mean patching everything again, including addresses the program has computed and stored in variables while running, which the loader cannot find. Execution-time binding avoids this by never changing the program at all.

### Example 3: Memory saved by shared libraries

Fifty processes each use a 2 MiB standard library.

| Linking | Library memory |
| :--- | :--- |
| Static: each process has its own copy | $50 \times 2 = 100$ MiB |
| Dynamic: one shared copy of the code | about 2 MiB of code, plus a small private data area per process |

Only the library's read-only **code** is shared. Each process still gets its own copy of the library's writable data, such as global variables, created when the process first writes to it.

## Applications

- **Every modern operating system** uses execution-time binding through an MMU, which makes multiprogramming, protection, and virtual memory possible.
- **Shared libraries** such as the C library, graphics libraries, and system frameworks are mapped into most processes on a system.
- **Address space layout randomization (ASLR)** loads programs and libraries at random addresses each run, which relies on relocatable or position-independent code and makes memory-corruption attacks harder.
- **Embedded systems without an MMU** still use compile-time or load-time binding and carefully planned fixed memory maps.
- **Plug-in architectures** in browsers, editors, and audio software use dynamic loading to add features at run time.

## Common mistakes

- **Thinking the limit register holds the highest physical address.** It holds the size of the region, and the check is applied to the logical address before relocation.
- **Assuming programs see physical addresses.** With execution-time binding, every address a program uses is logical.
- **Forgetting that only the code of a shared library is shared;** writable data is private to each process.
- **Treating dynamic loading and dynamic linking as the same thing.** Dynamic loading delays loading a routine; dynamic linking delays resolving references to library code.
- **Assuming load-time relocation allows moving a running process.** Only execution-time binding does.

## Revision notes

- Compiler → object file; linker → executable; loader → process in memory.
- Binding at compile time (absolute code), load time (relocatable code), or execution time (MMU translation).
- Logical (virtual) addresses are generated by the CPU; the MMU maps them to physical addresses.
- Base and limit: legal if $0 \le a < \text{limit}$; physical $= \text{base} + a$; otherwise trap. Provides relocation and protection.
- Dynamic loading loads routines on first use; dynamic linking shares library code among processes.
- Swapping moves whole processes (or, in modern systems, pages) between memory and disk.

## Practice questions

:::question basic
What is the difference between a logical address and a physical address?
:::answer
A logical (virtual) address is generated by the CPU when a program runs; it is the address the program itself uses. A physical address is the location actually sent to the memory hardware. With execution-time binding, the memory-management unit translates each logical address into a physical one, so the two generally differ.
:::

:::question basic
A process has base register 14000 and limit register 3000. Translate the logical addresses 0, 2999, and 3000.
:::answer
Logical 0 maps to $14000 + 0 = 14000$. Logical 2999 is less than the limit, so it maps to $14000 + 2999 = 16999$. Logical 3000 is not less than the limit, so the MMU traps to the operating system with an addressing error; it would otherwise have reached 17000, outside the process's region.
:::

:::question intermediate
Why must loading the base and limit registers be privileged instructions?
:::answer
The registers define which physical memory a process may access. If a user program could change them, it could set the base to point at the kernel's memory or another process's memory and set a large limit, bypassing all protection. Only the kernel, running in kernel mode during a context switch, may load them.
:::

:::question intermediate
Explain why execution-time binding is needed if the operating system wants to move a running process to a different area of memory.
:::answer
With load-time binding, the loader patched every address in the program when it was loaded, and the program may since have stored addresses in variables and on its stack. Moving the process would require finding and fixing all of them, which is impossible in general. With execution-time binding, the program uses only logical addresses, which do not change; the OS copies the process's memory to the new location and updates the base register, and all the program's addresses automatically refer to the new location.
:::

:::question intermediate
Give two advantages and one risk of dynamic linking with shared libraries.
:::answer
Advantages: a single copy of the library's code in physical memory serves every process that uses it, saving memory; and a library can be updated, for example to fix a security bug, without relinking every program that uses it. Risk: a new version of the library may change its behaviour or interface incompatibly, breaking programs that depended on the old version.
:::

:::question advanced
A system swaps whole processes to a disk that transfers 100 MB per second. How long does it take to swap a 500 MB process out and another 500 MB process in, and why does this make whole-process swapping unattractive?
:::answer
Each transfer takes $500 / 100 = 5$ seconds, so swapping one process out and another in takes about 10 seconds, ignoring seek time. During that time the swapped processes cannot run, and if this happened on every context switch the system would spend nearly all its time moving data. This is why modern systems swap individual pages only when memory is short, moving only the parts of a process that are actually needed or unused.
:::
