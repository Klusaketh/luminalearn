## Introduction

A database is only useful if each row can be found and referred to unambiguously. Two customers with the same name must still be distinguishable; an order must point to exactly one customer; and deleting a customer must not leave orders pointing at nobody. **Keys** identify rows, and **integrity constraints** state the rules the data must always obey.

Declaring keys and constraints in the schema, rather than checking them in application code, means the DBMS enforces them on every insert, update, and delete, from every program and every person. This lesson defines the different kinds of keys precisely, explains how foreign keys tie tables together, and shows what each **referential action** does when a referenced row changes, with real SQL that you can run.

**Before you start:** you should know the relational model (relations, tuples, attributes) and basic SQL table definitions.

## Core theory

### Kinds of keys

Let $R$ be a relation schema.

- A **superkey** is any set of attributes whose values are unique for every possible tuple of $R$. The set of all attributes is always a superkey.
- A **candidate key** is a **minimal** superkey: removing any attribute makes it no longer unique.
- The **primary key** is the candidate key chosen by the designer as the main identifier. It must never be NULL.
- **Alternate keys** are the candidate keys not chosen as primary; they are usually declared `UNIQUE`.
- A **composite key** is a key with more than one attribute, such as `(course_id, section_no)`.

For `Student(sid, email, name, dob)`, `{sid}` and `{email}` are candidate keys if both are unique by the university's rules; `{sid, name}` is a superkey but not a candidate key, because `sid` alone is already unique.

**Keys come from meaning, not from data.** A key is a statement about every state the database can ever be in. A sample of rows can show that an attribute set is **not** a key (by containing a duplicate), but it can never prove that one is.

### Natural and surrogate keys

- A **natural key** has meaning outside the database: an ISBN, a country code, an email address.
- A **surrogate key** is an artificial identifier generated by the system, such as an auto-incrementing integer or a UUID.

Natural keys can change (people change email addresses) and may be long or composite; surrogate keys are stable and compact. A common design is a surrogate primary key plus `UNIQUE` constraints on the natural candidate keys, which keeps the uniqueness rule while giving stable references.

### Foreign keys

A **foreign key** is a set of attributes in one table (the **referencing** or child table) whose values must match the primary key, or another unique key, of a row in a **referenced** (parent) table, or be NULL. A foreign key can reference its own table, such as `employee.manager_id REFERENCES employee(id)`.

### Integrity constraints

| Constraint | Rule | SQL |
| :--- | :--- | :--- |
| Domain | values come from the attribute's type and allowed set | column types, `CHECK` |
| Entity integrity | primary-key values are unique and never NULL | `PRIMARY KEY` |
| Referential integrity | foreign-key values match an existing referenced key, or are NULL | `REFERENCES` |
| Key (uniqueness) | alternate keys are unique | `UNIQUE` |
| Required values | the attribute must have a value | `NOT NULL` |
| Semantic rules | any condition on a row | `CHECK (salary > 0)` |

A `UNIQUE` column may contain several NULLs in most DBMSs, because NULLs are not considered equal to each other.

### Referential actions

When a parent row is **deleted** or its key is **updated**, existing child rows would be left with dangling references. The foreign key's actions decide what happens:

| Action | Effect on child rows |
| :--- | :--- |
| `NO ACTION` / `RESTRICT` (default) | the change to the parent is refused while children reference it |
| `CASCADE` | children are deleted too (on delete), or their foreign keys updated to the new value (on update) |
| `SET NULL` | children's foreign keys become NULL (the column must allow NULL) |
| `SET DEFAULT` | children's foreign keys become the column's default value, which must itself exist in the parent |

`RESTRICT` and `NO ACTION` differ only in when the check happens: `RESTRICT` checks immediately, while `NO ACTION` checks at the end of the statement (or of the transaction, if the constraint is deferred).

Choose actions from the meaning of the relationship: deleting an order should cascade to its order lines (they cannot exist alone), but deleting a department should probably not delete its employees; `SET NULL` or a refusal is safer.

## Worked examples

### Example 1: Which attribute sets are unique in a sample?

```python
from itertools import combinations

attributes = ("sid", "email", "name", "dob")
rows = [(1, "asha@uni.edu", "Asha", "2004-03-14"), (2, "ben@uni.edu", "Ben", "2003-11-02"),
        (3, "chen@uni.edu", "Chen", "2004-03-14"), (4, "dara@uni.edu", "Asha", "2002-01-20")]

def unique_in_sample(columns):
    positions = [attributes.index(c) for c in columns]
    values = [tuple(row[p] for p in positions) for row in rows]
    return len(set(values)) == len(values)

superkeys = [set(cols) for n in range(1, len(attributes) + 1)
             for cols in combinations(attributes, n) if unique_in_sample(cols)]
minimal = [s for s in superkeys if not any(other < s for other in superkeys)]
print(len(superkeys), "attribute sets are unique in this sample")
print("minimal ones:", [sorted(s, key=attributes.index) for s in minimal])
```

Output:

```text
13 attribute sets are unique in this sample
minimal ones: [['sid'], ['email'], ['name', 'dob']]
```

In this sample, `sid` and `email` are unique, and so is the pair (name, date of birth). The first two are genuine candidate keys because the university assigns unique IDs and email addresses. The pair is unique only by luck: two different people can share a name and a birthday, and the next student admitted could prove it. This is why keys must be decided from the meaning of the data, never discovered from a sample.

### Example 2: Constraints and referential actions in SQL

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("PRAGMA foreign_keys = ON")              # SQLite enforces foreign keys only when enabled
db.executescript("""
CREATE TABLE department (code TEXT NOT NULL PRIMARY KEY, name TEXT NOT NULL UNIQUE);
CREATE TABLE employee (
    id INTEGER PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,                     -- alternate key
    name TEXT NOT NULL,
    dept TEXT REFERENCES department(code) ON UPDATE CASCADE ON DELETE SET NULL,
    salary INTEGER CHECK (salary > 0)
);
CREATE TABLE project (
    id INTEGER PRIMARY KEY,
    lead_id INTEGER NOT NULL REFERENCES employee(id)   -- no action: deletion is refused
);
INSERT INTO department VALUES ('ENG', 'Engineering'), ('OPS', 'Operations');
INSERT INTO employee VALUES (1, 'asha@corp.example', 'Asha', 'ENG', 90000),
                            (2, 'ben@corp.example', 'Ben', 'OPS', 70000);
INSERT INTO project VALUES (100, 1);
""")

def attempt(sql):
    try:
        db.execute(sql)
        return "ok"
    except sqlite3.IntegrityError as error:
        return f"rejected: {error}"

for sql in [
    "INSERT INTO employee VALUES (3, 'asha@corp.example', 'A. Rao', 'ENG', 80000)",  # duplicate email
    "INSERT INTO employee VALUES (3, 'chen@corp.example', 'Chen', 'HR', 60000)",     # no such dept
    "INSERT INTO employee VALUES (3, 'chen@corp.example', 'Chen', 'ENG', -5)",       # bad salary
    "INSERT INTO department VALUES (NULL, 'Finance')",                               # NULL key
    "UPDATE department SET code = 'SWE' WHERE code = 'ENG'",                         # cascades
    "DELETE FROM department WHERE code = 'OPS'",                                     # sets NULL
    "DELETE FROM employee WHERE id = 1",                                             # refused
]:
    print(attempt(sql))
print(db.execute("SELECT id, name, dept FROM employee ORDER BY id").fetchall())
```

Output:

```text
rejected: UNIQUE constraint failed: employee.email
rejected: FOREIGN KEY constraint failed
rejected: CHECK constraint failed: salary > 0
rejected: NOT NULL constraint failed: department.code
ok
ok
rejected: FOREIGN KEY constraint failed
[(1, 'Asha', 'SWE'), (2, 'Ben', None)]
```

The first four statements each break one rule and are rejected: an alternate key, referential integrity, a `CHECK`, and entity integrity. Renaming department `ENG` to `SWE` cascades, so Asha's row follows it automatically. Deleting `OPS` sets Ben's department to NULL rather than deleting Ben. Deleting Asha is refused, because project 100 still names her as its lead and that foreign key has no action. Two SQLite details: foreign keys are enforced only after `PRAGMA foreign_keys = ON`, and, for historical reasons, a non-integer `PRIMARY KEY` column accepts NULL unless it is also declared `NOT NULL`, which is why `code` is declared that way here.

### Example 3: Choosing referential actions

| Relationship | On delete of the parent | Reason |
| :--- | :--- | :--- |
| order → order_line | `CASCADE` | lines have no meaning without their order |
| customer → order | `RESTRICT` | orders are financial records; deleting a customer with orders should be refused |
| department → employee | `SET NULL` | employees remain when a department closes, awaiting reassignment |
| product → review | `CASCADE` or `RESTRICT` | a business decision: remove reviews with the product, or forbid deleting reviewed products |
| employee → employee (manager) | `SET NULL` | when a manager leaves, their reports have no manager until one is assigned |

Cascading deletes are convenient but dangerous when chained: one delete can remove large amounts of data across several tables, so `CASCADE` should be reserved for children that are genuinely part of their parent.

## Applications

- **Every relational schema** declares primary keys; ORMs such as Django and Rails add a surrogate `id` column by default.
- **Data quality:** `UNIQUE` on emails and usernames, `CHECK` on ranges, and `NOT NULL` on required fields stop bad data at the source.
- **Referential integrity in commerce:** orders, invoices, and payments reference customers and products through foreign keys, so reports never show orphaned records.
- **Data import and migration:** constraint violations during an import reveal duplicates and broken references in the source data.
- **Performance:** DBMSs build an index for every primary key and unique constraint, and optimizers use key information to simplify joins.

## Common mistakes

- **Calling every unique attribute set a candidate key.** Candidate keys must be minimal; `{sid, name}` is a superkey, not a candidate key.
- **Inferring keys from sample data,** which can only disprove uniqueness, never prove it.
- **Choosing a natural key that can change,** such as an email address, as the primary key referenced by many tables.
- **Using `ON DELETE CASCADE` everywhere,** which can silently delete large amounts of related data.
- **Forgetting that some DBMSs need foreign-key enforcement enabled** (SQLite's `PRAGMA foreign_keys = ON`) or allow NULLs in primary keys without `NOT NULL`.
- **Using `SET NULL` on a column declared `NOT NULL`,** which makes the deletion fail.

## Revision notes

- Superkey: unique attribute set. Candidate key: minimal superkey. Primary key: the chosen candidate key, never NULL. Alternate keys: the other candidate keys (`UNIQUE`).
- Keys are semantic rules about all possible states, not observations about current data.
- Surrogate keys are stable and compact; natural keys carry meaning; combine a surrogate primary key with `UNIQUE` natural keys.
- Foreign key: values must match a referenced key or be NULL; may reference the same table.
- Constraints: domain, entity integrity, referential integrity, `UNIQUE`, `NOT NULL`, `CHECK`.
- Referential actions: `NO ACTION`/`RESTRICT` (refuse), `CASCADE`, `SET NULL`, `SET DEFAULT`.

## Practice questions

:::question basic
What is the difference between a superkey and a candidate key?
:::answer
A superkey is any set of attributes that uniquely identifies every tuple. A candidate key is a superkey with no unnecessary attributes: if any attribute is removed, it is no longer unique. Every candidate key is a superkey, but supersets of candidate keys are superkeys that are not candidate keys.
:::

:::question basic
A relation `Car(vin, plate, make, model)` has two candidate keys, `vin` and `plate`. If `vin` is chosen as the primary key, what is `plate`, and how should it be declared?
:::answer
`plate` is an alternate key. It should be declared `UNIQUE` (and `NOT NULL` if every car must have a plate), so that the DBMS still enforces its uniqueness even though it is not the primary key.
:::

:::question intermediate
How many superkeys does a relation $R(A, B, C, D)$ have if its only candidate key is $\{A\}$? What if the candidate keys are $\{A\}$ and $\{B\}$?
:::answer
With the single key $\{A\}$, a superkey is any set containing $A$: the other three attributes can each be in or out, so there are $2^3 = 8$ superkeys. With keys $\{A\}$ and $\{B\}$, count the sets containing $A$ or $B$: there are 16 subsets of $\{A, B, C, D\}$, and the 4 that contain neither $A$ nor $B$ (subsets of $\{C, D\}$) are excluded, leaving 12 superkeys.
:::

:::question intermediate
`orders.customer_id` references `customer(id)` with `ON DELETE SET NULL`, and `order_line.order_id` references `orders(id)` with `ON DELETE CASCADE`. What happens when a customer is deleted, and when an order is deleted?
:::answer
Deleting a customer keeps their orders but sets `customer_id` to NULL in each of them (so `customer_id` must be nullable); the order lines are unaffected, because their orders still exist. Deleting an order deletes all of its order lines automatically through the cascade.
:::

:::question intermediate
Why might a designer use a surrogate key for a `person` table even though `email` is unique?
:::answer
Email addresses change, and if `email` were the primary key, every foreign key referencing a person would have to be updated whenever someone changes address. They are also relatively long, making indexes and foreign keys larger. A surrogate integer key never changes and is compact. The designer still declares `email UNIQUE` so that the uniqueness rule is enforced.
:::

:::question advanced
A table `employee(id, name, manager_id)` has `manager_id REFERENCES employee(id)`. What referential action would you choose for deleting an employee, and what problem could `ON DELETE CASCADE` cause here?
:::answer
`ON DELETE SET NULL` is usually appropriate: when a manager leaves, their reports remain employees and simply have no manager until one is assigned (or `RESTRICT`, forcing reassignment before deletion). `ON DELETE CASCADE` on a self-reference would delete every report of the departing manager, then every report of those reports, and so on down the hierarchy; deleting the CEO would delete the whole company's employee records.
:::
